## 1. 背景与目标

### 1.1 背景

模块 002 已把多源聊天记录（微信/iMessage/微博/Instagram/照片）标准化为统一的 `Conversation`（`List<Message>` + 参与者 + 统计）。但标准化的消息流本身还不是"人"——它只是原始素材。要让用户"与失去的人继续对话"，必须先把这些素材**蒸馏**成一个结构化、可复现、可解释的人格模型（Persona）。

这正是 Lostone 的核心价值所在："将回忆蒸馏成 AI Persona，不是为了挽回，是为了记住。" Persona 是后续所有对话能力（模块 004 本地模型、005 云端 API、006 聊天界面）的输入基石：对话系统不直接读原始聊天记录，而是读 Persona。

### 1.2 目标

- 从一段 `Conversation` **确定性地**提取出目标人物的五层人格模型（硬规则 / 身份 / 表达风格 / 情感逻辑 / 关系行为）。
- 产出一个自包含、可序列化、可版本化的 `.persona` 文件（JSON），作为对话系统与 Persona 浏览器的唯一数据来源。
- 支持**增量更新**：用户后续导入新记录时 merge 进现有 Persona，而不是重新生成、不覆盖已有结论。
- 全程**本地、离线、无网络、无 LLM**，可完全单元测试，与项目隐私优先原则（ADR-002/隐私要求）一致。

### 1.3 范围

**包含**：
- 记忆提取（时间线构建、关键事件识别、偏好/习惯提取）。
- 性格分析（语言风格：口头禅、标点、表情习惯；情感模式：依恋/冲突信号；标签生成）。
- 五层 Persona 数据模型与 `.persona` JSON 序列化/反序列化。
- Persona Builder：整合五层、写入元信息、版本管理、增量更新（merge）。
- Prompt 模板系统：把 Persona 渲染为可供 LLM 使用的 system prompt（纯字符串产物，不发起任何推理）。
- 生成质量的可解释性（每条结论可回溯到证据消息）。

**不包含**：
- 任何 LLM / 神经网络推理或云端调用（属模块 004/005）。
- 实际对话、消息生成、上下文管理（属模块 006）。
- Persona 的可视化 UI、编辑界面（属 Phase 4 UI）。
- 多语言 NLP 深度语义分析（初版以中文为主、基于统计与规则；深度语义留待后续）。
- 加密存储与生物识别（属模块 008；本模块只产出明文 JSON，交由存储层加密）。
- **群聊多人格拆分**：v1 仅正式支持 **1:1 会话**（用户 ↔ 单一目标人物）。多方会话只要未显式指定 `personSenderIds` 即走守卫降级（低置信 + 标记切分不可靠；`myIdentifiers` 不抑制该守卫），不臆断把多人并入单一人格；完整群聊支持留待后续。

## 2. 用户故事

### 故事 1：丧亲用户 - 生成 Persona - 重建话语风格

**作为**：一位刚导入了与已故母亲三年微信记录的用户
**我想要**：一键把这些记录生成成"妈妈"的 Persona
**以便于**：后续能和一个说话方式、口头禅、关心方式都像妈妈的 AI 对话

**验收标准**：
- [ ] 给定一段含 ≥ 200 条目标人物消息的 `Conversation`，当调用生成，则产出包含完整五层结构的 Persona。
- [ ] 给定生成结果，当查看表达风格层，则能看到从真实消息统计出的高频口头禅/表情/标点习惯（每项附出现次数）。
- [ ] 给定 1000 条消息，当生成，则在 60 秒内完成（见 §4.1）。

**优先级**：高

---

### 故事 2：用户 - 增量补充 - 不丢失已有回忆

**作为**：一位半年前已生成 Persona 的用户
**我想要**：把新翻出来的一批旧聊天记录追加进去
**以便于**：Persona 更完整，且不推翻我上次已经认可的结果

**验收标准**：
- [ ] 给定一个已存在的 Persona 和一批新消息，当执行增量更新，则时间线、关键事件、风格统计被 merge 且 `version` 递增。
- [ ] 给定增量更新，当新旧数据冲突（如时间段延长），当合并，则保留可追溯的历史而非静默丢弃。
- [ ] 给定重复导入相同消息，当增量更新，则去重、结果幂等（不重复计数）。

**优先级**：高

---

### 故事 3：用户 - 理解生成依据 - 建立信任

**作为**：一位担心"AI 瞎编"的用户
**我想要**：看到每个人格结论背后的真实证据
**以便于**：相信这个 Persona 真的来自我们的聊天，而不是模型幻觉

**验收标准**：
- [ ] 给定任一表达风格/情感/偏好结论，当查看，则能定位到支撑它的样本消息（或消息计数与示例）。
- [ ] 给定素材不足（消息过少），当生成，则明确标注低置信度而非编造。

**优先级**：中

---

### 故事 4：开发者 - 稳定的 Persona 契约 - 对接对话系统

**作为**：模块 004/005/006 的实现者
**我想要**：一个稳定、版本化、Schema 明确的 `.persona` 文件与 Prompt 渲染接口
**以便于**：对话系统只依赖 Persona，而不必理解各数据源的原始格式

**验收标准**：
- [ ] 给定一个 `.persona` 文件，当被反序列化，则能无损还原为 Persona 对象。
- [ ] 给定 Persona，当渲染 system prompt，则得到确定性的、不含隐私原文之外内容的字符串。
- [ ] 给定 schema 版本升级，当读取旧文件，则按迁移规则兼容或明确报错（不静默损坏）。

**优先级**：中

## 3. 功能清单

### 3.1 核心功能

#### 功能 1：记忆提取（MemoriesAnalyzer）
**描述**：从 `Conversation` 中提取结构化"记忆"——时间线、关键事件、偏好/习惯。

**输入**：`Conversation`（预处理后的消息，已去重、按时间升序）+ 目标人物标识（默认以 `Message.isFromMe==false` 判对方，`personSenderIds`/`myIdentifiers` 覆盖细化，见 ERD §4.2）。

**输出**：`Memories`（时间线区间、关键事件列表、偏好/习惯统计）。

**业务规则**：
- 时间线：起止时间、活跃时段（小时分布）、消息频次趋势。
- 关键事件：基于频次骤变、长文本、纪念性关键词（生日/节日/称呼变化等）的启发式标记，附证据（消息键哈希）。
- 偏好/习惯：高频名词短语、常提及的人/地点/活动（基于统计，不做深度 NLP）。
- 仅统计目标人物的消息用于"人格"，用户自己的消息（`isFromMe==true` 或命中 `myIdentifiers`）仅用于关系行为对照，绝不计入逝者人格。
- 默认切分依赖模块 002 可靠填充 `Message.isFromMe`。两类**守卫降级**门控不同（`myIdentifiers` 只能定"我"、无法在多个对方中指出目标）：①方向不可判定（非空会话 `isFromMe` 全为 `false`）——`personSenderIds` 与 `myIdentifiers` **皆未传**时触发；②多方会话（>1 目标发送者）——**仅** `personSenderIds` 未传即触发（`myIdentifiers` 不抑制，避免群聊里非我方多人被静默并成一个人格）。触发时各层标低置信、`segmentationResolved=false`，不臆断把全体并入人格，提示用户手动指定目标人物后重建（空会话/无目标场景不触发）。

**优先级**：P0

---

#### 功能 2：性格分析（PersonaAnalyzer）
**描述**：从目标人物消息中统计语言风格与情感模式，并生成标签。

**输入**：目标人物 `List<Message>` + `Memories`。

**输出**：表达风格、情感逻辑草稿 + 标签集合。

**业务规则**：
- 语言风格：口头禅（高频短语/句首词）、标点习惯（如省略号、感叹号密度）、表情/emoji 使用 Top-N（均附计数）。
- 情感模式：正/负情感词密度、称呼亲密度、道歉/安慰/关心类话语模式（关键词规则，可解释）。
- 标签：由统计特征映射为有限标签集（如"话痨/惜字如金"、"爱用表情"、"报喜不报忧"），每个标签附触发依据。
- 素材不足阈值：目标人物消息 < 阈值（见 Spec）时，相关层标 `confidence: low`。

**优先级**：P0

---

#### 功能 3：五层 Persona 模型与 `.persona` 序列化
**描述**：定义 Persona 五层数据结构与 JSON 文件格式，支持无损往返。

**输入**：五层各自的结构化结果 + 元信息（人物名、关系、来源、schema 版本、生成时间）。

**输出**：`Persona` 对象 + `.persona`（JSON）文件字节。

**业务规则**：
- 层次：`hardRules` / `identity` / `expressionStyle` / `emotionalLogic` / `relationalBehavior`，缺失层用空但存在的结构占位（不产 null 层）。
- 文件含 `schemaVersion`、`personaVersion`、`generatedAt`、`source`（即 `PersonaSource`，PRD 内也称"来源摘要 / sourceSummary"，含数据源/消息数/时间跨度/版本修订轨迹 `revisions`）。
- 证据只存**消息键哈希**（SHA-256）+ 计数 + 可选短示例，不落逐条原文（隐私约束，见 ERD §1.2/§8.1）。
- `fromJson(toJson(p)) == p`（值相等）。

**优先级**：P0

---

#### 功能 4：Persona Builder（整合 + 版本 + 增量）
**描述**：编排上述分析器，整合五层，管理版本与增量更新。

**输入**：`Conversation`（首次）或（现有 `Persona` + 新 `Conversation`）（增量）。

**输出**：新的/更新后的 `Persona`。

**业务规则**：
- 首次生成：全量分析 → 组装五层 → `personaVersion = 1`。
- 增量更新：合并消息集（按**消息内容键的 SHA-256 哈希**去重，底层键与模块 002 `DataPreprocessor` 去重键一致，非 `Message.id`）→ 重算受影响统计 → merge 记忆/风格 → `personaVersion += 1`，并向 `PersonaSource.revisions` 追加一条版本快照（可追溯历史，兑现用户故事 2「不静默丢弃」）。
- 硬规则层为**用户可编辑的显式禁忌**，增量更新**永不覆盖**用户已设置的硬规则。
- 幂等：对同一批消息重复更新不改变结果（除 version 语义外）。

**优先级**：P0

---

#### 功能 5：Prompt 模板系统
**描述**：把 Persona 渲染为可供下游 LLM 使用的 system prompt 字符串。

**输入**：`Persona` + 模板选项（语气/长度档位）。

**输出**：确定性的 prompt 字符串。

**业务规则**：
- 纯字符串拼装，不发起任何推理/网络。
- 模板可版本化；同一 Persona + 同一模板 → 同一输出。
- 渲染内容仅来自 Persona 字段，不注入未经 Persona 记录的信息。

**优先级**：P1

---

### 3.2 辅助功能

#### 功能 A：置信度与可解释性元数据
**描述**：为每层/关键结论附 `confidence` 与证据引用（**消息键哈希**、计数、可选短示例；哈希底层键与模块 002 去重键一致、跨导入稳定且不可逆还原原文），支撑故事 3。

**优先级**：P1

#### 功能 B：Persona 摘要（人类可读）
**描述**：生成一段简短的自然语言摘要（模板拼装，非 LLM），用于 UI 预览。

**优先级**：P2

## 4. 非功能性需求

### 4.1 性能要求
- **生成时间**：≤ 60 秒 / 1000 条消息（对齐 CLAUDE.md 性能指标"Persona 生成"）。
- **增量更新**：仅重算受影响部分，典型追加（<20% 新增量）应显著快于全量。
- **内存**：与消息数量线性相关，峰值内存不因单次生成显著超过语料本身规模（避免多份全量拷贝）。

### 4.2 安全与隐私要求
- 全程本地、离线、无网络、无第三方上传。
- `.persona` 由本模块产出明文 JSON，**加密由存储层（模块 008）负责**；本模块不得把敏感原文写入日志。
- 可解释性引用只存**消息键哈希（SHA-256）** / 计数 / 一条截断短示例（≤ 60 字素簇），**绝不持久化逐条原文**；`.persona` 体积因此不随聊天量线性膨胀。

### 4.3 可用性要求
- 素材不足、无目标人物消息、空会话等情况必须给出明确结果或错误，不得崩溃、不得编造。

### 4.4 兼容性要求
- 纯 Dart 实现，随 Flutter 应用运行于 iOS/macOS；不依赖平台原生能力。
- `.persona` `schemaVersion` 向后兼容策略：可读旧版或明确报迁移错误。

## 5. 数据要求

### 5.1 数据输入
| 数据项 | 类型 | 必填 | 来源 | 验证规则 |
|--------|------|------|------|----------|
| conversation | `Conversation` | 是 | 模块 002 | 非空消息列表 |
| personSenderIds | `Set<String>` | 否 | 用户选择 | 为空时默认以 `Message.isFromMe==false` 判对方，`myIdentifiers` 细化；方向不可判定/多方会话时触发守卫降级（分支门控见功能1）|
| existingPersona | `Persona?` | 否 | 上次生成 | 增量更新时提供 |
| options | `PersonaBuildOptions` | 否 | 调用方 | 阈值/模板档位 |

### 5.2 数据输出
| 数据项 | 类型 | 格式 | 说明 |
|--------|------|------|------|
| persona | `Persona` | 内存对象 | 五层 + 元信息 |
| .persona 文件 | bytes | JSON(UTF-8) | 可序列化产物 |
| systemPrompt | `String` | 纯文本 | 供下游 LLM |

### 5.3 数据存储
- 存储位置：应用私有目录（由存储层管理）。
- 存储格式：JSON（`.persona`）；未来可评估 Protobuf（见 ADR-003，暂不采用）。
- 数据保留：随 Persona 生命周期，用户可删除。

## 9. 测试策略

### 9.1 单元测试
- 覆盖率目标：> 80%。
- 重点：各分析器统计正确性、五层序列化往返、增量 merge 幂等/去重、置信度阈值、Prompt 渲染确定性。

### 9.2 集成测试
- 端到端：合成 `Conversation` → 生成 Persona → 增量再生成 → 断言 merge 结果与 version。

### 9.3 用户验收测试（UAT）
- 用合成/授权数据人工评审生成质量（≥ 3 人主观评分），验证"像不像"。
