## 1. 背景与目标

### 1.1 背景
Lostone 的核心是把逝去之人留下的历史对话，蒸馏成可对话的 AI Persona。要做到这一点，第一步是把散落在各处的原始记忆**导入并结构化**：
- 聊天记录分布在微信、iMessage、微博、Instagram 等多个平台；
- 每个平台的导出格式各不相同（CSV、HTML、JSON、SQLite）；
- 原始数据含有大量噪声（系统消息、重复消息、乱序、无效字符）；
- 照片里也藏着时间和地点等可用于重建时间线的元数据。

如果没有一个统一、可靠、可扩展的导入层，后续的 Persona 生成引擎（模块 003）将拿不到干净、标准化的输入。

### 1.2 目标
构建一个**多源、可扩展、隐私优先**的数据导入模块，能够：
- ✅ 让用户从本地选择聊天/数据文件（CSV、JSON、TXT、HTML）
- ✅ 解析主流数据源（微信、iMessage、微博、Instagram、照片 EXIF）
- ✅ 将异构数据统一为标准化的 `Message` / `Conversation` 模型
- ✅ 对数据进行清洗、去重、按时间排序
- ✅ 输出结构化 JSON，供 Persona 生成引擎消费
- ✅ 全程本地处理，不上传任何用户数据

### 1.3 范围

**包含**：
- 文件选择器（CSV / JSON / TXT / HTML）
- 数据预处理管线（清洗、去重、时间排序）
- 微信聊天记录解析器（CSV、HTML）
- iMessage 解析器（iOS 导出文件、macOS `chat.db`）
- 照片 EXIF 元数据提取（拍摄时间、地理位置、时间线）
- 社交媒体解析器（微博 JSON、Instagram JSON）
- 统一数据模型与标准化输出（结构化 JSON）
- 导入结果预览与统计（消息数、时间跨度、参与者）

**不包含**：
- Persona 生成逻辑（模块 003）
- 云端同步或跨设备导入（本项目 100% 本地）
- 语音/图片内容的 AI 理解（仅提取与归档，不做识别）
- **媒体转码/压缩**（v1 原样保存，不转码）
- 数据的长期加密存储方案（模块 008 数据安全）
- 导入 UI 的最终视觉设计稿（本 PRD 只定义流程与信息架构）

### 1.3.1 解析产物（三层模型）

真实导出（如一份约 5GB 的微信记录）中约 99% 是媒体字节，真正的文本信号仅几十 MB。因此解析产物**分三层**，各自独立管理，避免把"文本蒸馏"和"海量字节搬运"混为一谈：

| 层 | 内容 | 存什么 | 规模 |
|----|------|--------|------|
| **文本语料** | 全部文本消息 | 结构化 `Message`（SQLite/JSON） | 几十 MB |
| **媒体索引** | 每个图片/视频/语音一条记录 | `type` + `timestamp` + `senderId` + `mediaPath`，**只存路径不存字节** | 小 |
| **媒体字节** | 实际媒体文件 | 按分级档位拷贝/引用（见 §1.4 决策 4） | 可达数 GB |

- 文本语料是 Persona 燃料，也是可浏览历史；**文本层与媒体索引层恒存**。
- 媒体字节层的处理量由用户选择的分级档位决定，与文本解析解耦。

### 1.4 关键产品决策

**决策 1：保留对话双方（不丢弃"我"发出的消息）**
导入时通过 `isFromMe` 同时保留双方消息，而非只保留逝者一方。
**理由**：Persona 的说话风格依赖于**对话上下文**——同样的话，回应不同的问题语气不同；只留单侧会丢失语境，降低 Persona 质量。用户消息在生成阶段（模块 003）可再降权，但导入阶段不应提前丢弃信息。

**决策 2：首批数据源的取舍**
首批支持微信、iMessage、微博、Instagram、照片，**优先中文市场高频、且导出格式可得**的渠道：微信/微博覆盖国内主要社交场景，iMessage 覆盖 Apple 生态，Instagram 覆盖海外，照片提供时间线锚点。
**暂缓（列入 ROADMAP 待排期，非遗漏）**：Android 短信（SMS Backup XML/CSV，格式稳定、成本低，建议下一批优先）、豆瓣、小红书、PDF/纯文本粘贴。取舍依据是"数据可得性 + 用户覆盖 / 实现成本"。

**决策 3：平台存储分工**（owner 已确认）
- **iOS**：经 zip + AirDrop +「用其他应用打开」导入 → 解压进 App 沙盒 → App **自持有**媒体副本；媒体目录标记 `isExcludedFromBackup`，避免撑爆 iCloud 备份、规避 App Review 风险。
- **macOS**：通过 security-scoped bookmark **就地引用**原始文件，不拷贝。
**理由**：iOS 沙盒模型要求 App 自持有文件；macOS 桌面文件长期可达，就地引用最省空间。

**决策 4：媒体导入分级（默认档 = 全部媒体）**（owner 已确认）
提供三档，用户可选；**文本语料与媒体索引恒存**，本档位仅决定"媒体字节"层的拷贝范围：
- 仅文本（只存文本 + 媒体索引路径）
- 仅照片 + 语音
- **全部媒体（默认）**
**理由**：owner 选择完整保留记忆；因默认可能占用数 GB，导入前须明确提示预计占用空间，并（iOS）确保媒体目录 `isExcludedFromBackup`。

## 2. 用户故事

### 故事 1：用户 - 导入微信聊天记录 - 重建与逝者的对话

**作为**：一名失去亲人的用户
**我想要**：把导出的微信聊天记录文件导入 App
**以便于**：让 App 学习对方的说话风格，重建 Persona

**验收标准**：
- [ ] 给定一份微信导出的 CSV/HTML 文件，当我选择并导入后，则 App 显示解析出的消息条数和时间跨度
- [ ] 给定包含文本、图片、语音的聊天记录，当解析后，则各类消息都被正确识别并归类
- [ ] 给定 1000+ 条真实聊天记录，当导入后，则在 60 秒内完成解析

**优先级**：高

---

### 故事 2：用户 - 导入 iMessage 记录 - 补充更多对话素材

**作为**：使用 iPhone/Mac 的用户
**我想要**：导入 iMessage 的聊天记录
**以便于**：为 Persona 提供更多真实语料

**验收标准**：
- [ ] 给定一份 iOS 导出的消息文件，当导入后，则消息被正确解析
- [ ] 给定 macOS 的 `chat.db` 文件，当导入后，则指定联系人的消息被提取
- [ ] 给定发出/收到两个方向的消息，当解析后，则 `isFromMe` 字段正确区分双方

**优先级**：高

---

### 故事 3：用户 - 导入照片元数据 - 重建记忆时间线

**作为**：想丰富记忆细节的用户
**我想要**：导入照片并提取其中的时间、地点信息
**以便于**：构建一条按时间排序的记忆时间线

**验收标准**：
- [ ] 给定一批含 EXIF 的照片，当导入后，则提取出拍摄时间
- [ ] 给定含 GPS 信息的照片，当用户授权后，则提取地理位置（可选）
- [ ] 给定无 EXIF 的照片，当导入后，则跳过并在结果中记录警告，不中断流程

**优先级**：中

---

### 故事 4：用户 - 获得干净的数据 - 提升 Persona 质量

**作为**：用户
**我想要**：导入的数据自动去除噪声、去重、按时间排序
**以便于**：Persona 学到的是真实、连贯的对话，而非系统消息和垃圾数据

**验收标准**：
- [ ] 给定含系统消息（"你已添加对方为好友"）的记录，当预处理后，则系统消息被过滤
- [ ] 给定含完全重复消息的记录，当预处理后，则重复项被去除
- [ ] 给定时间乱序的消息，当预处理后，则按时间升序排列

**优先级**：高

---

### 故事 5：开发者 - 扩展新数据源 - 低成本接入新平台

**作为**：贡献者/开发者
**我想要**：一个统一的解析器接口
**以便于**：只需实现一个 `DataParser` 就能接入新的数据源，无需改动主流程

**验收标准**：
- [ ] 给定一个新的解析器类，当它实现 `DataParser` 接口后，则可被导入管线自动调度
- [ ] 给定统一数据模型，当新解析器输出 `Message` 列表后，则下游预处理与标准化无需改动

**优先级**：中

## 3. 功能清单

### 3.1 核心功能

#### 功能 1：文件选择器
**描述**：让用户从本地文件系统选择要导入的数据文件

**输入**：
- 支持的扩展名：`.csv`、`.json`、`.txt`、`.html`、`.db`、图片（`.jpg`/`.jpeg`/`.png`/`.heic`）

**输出**：
- 选中文件的路径列表

**业务规则**：
- 支持多选
- 校验文件扩展名与大小上限（单文件 ≤ 200 MB）
- 不支持的类型给出明确提示

**优先级**：P0

---

#### 功能 2：数据预处理管线
**描述**：对解析出的消息统一执行清洗、去重、排序

**处理步骤**：
1. **清洗**：去除无效/控制字符、过滤系统消息、去除空消息
2. **去重**：基于 `(source, senderId, timestamp, content)` 去除完全重复项
3. **时间排序**：按 `timestamp` 升序排列

**优先级**：P0

---

#### 功能 3：微信聊天记录解析器
**描述**：解析微信导出的聊天记录

**支持格式**：CSV、HTML

**提取内容**：
- 文本消息
- 图片消息（记录引用/路径，不做内容识别）
- 语音消息（记录引用/路径与时长）
- 发送方/接收方、时间戳

**优先级**：P0

---

#### 功能 4：iMessage 解析器
**描述**：解析 iMessage 数据

**支持来源**：
- iOS 导出文件
- macOS `chat.db`（SQLite，指定联系人/会话）

**提取内容**：
- 文本消息、时间戳、发送方向（`isFromMe`）
- 附件引用

**优先级**：P0

---

#### 功能 5：照片 EXIF 元数据提取
**描述**：从照片中提取元数据并生成时间线

**提取内容**：
- 拍摄时间（`DateTimeOriginal`）
- 地理位置（GPS，可选，需用户授权）
- 生成按时间排序的记忆时间线条目

**优先级**：P1

---

#### 功能 6：社交媒体解析器
**描述**：解析社交媒体数据导出

**支持来源**：
- 微博 JSON
- Instagram JSON

**提取内容**：
- 帖子/私信文本、时间戳、作者

**优先级**：P1

---

#### 功能 7：数据标准化与导出
**描述**：将所有来源统一为标准模型并导出结构化 JSON

**输出**：
- `Conversation`（包含 `Message` 列表 + 元信息）
- 结构化 JSON 文件（供模块 003 消费）
- 导入统计（消息数、时间跨度、参与者、跳过/告警数）

**优先级**：P0

---

### 3.2 辅助功能

#### 功能 A：导入结果预览
**描述**：导入后展示消息条数、时间范围、参与者、样例消息与告警

**优先级**：P1

---

#### 功能 B：解析器自动识别
**描述**：根据文件内容/结构自动匹配合适的解析器，减少用户手动选择

**优先级**：P2

## 4. 非功能性需求

### 4.1 性能要求
真实导出可达数 GB / 10 万条以上，故性能目标按**大规模**制定，且**峰值内存必须与文件大小解耦**（流式处理，不得全量载入）：
- **解析吞吐**：≥ 5,000 条文本消息/分钟（10 万条 ≤ 20 分钟，可后台进行）
- **峰值内存**：< 300 MB，**与输入文件大小无关**（5GB 文件同样成立）
- **文件/目录选择响应**：< 1 秒
- **预处理（去重+排序）**：10 万条 < 30 秒
- **媒体拷贝**：流式拷贝，进度可见、可取消；不计入上述内存预算

### 4.2 安全与隐私要求
- 100% 本地解析，**不上传任何用户数据**
- 不在日志中输出消息正文等敏感内容
- 地理位置提取需用户**显式授权**
- 导出的中间 JSON 位于应用私有目录

### 4.3 可用性要求
- 单个文件解析失败不影响其他文件（隔离失败）
- 所有错误提供可读的中文提示与修复建议
- 部分解析成功时返回已解析部分 + 告警列表

### 4.4 兼容性要求
- **平台**：iOS 17+、macOS 14+
- **数据源版本**：以 2026 年主流导出格式为准，格式变更以解析器版本迭代应对

## 5. 数据要求

### 5.1 数据输入
| 数据项 | 类型 | 必填 | 来源 | 验证规则 |
|--------|------|------|------|----------|
| 数据文件 | File | 是 | 用户选择 | 支持的扩展名，≤ 200 MB |
| 数据源类型 | Enum | 否 | 用户选择/自动识别 | wechat/imessage/weibo/instagram/photo |
| 目标联系人 | String | 否 | 用户输入（chat.db） | 非空（macOS chat.db 场景） |
| 地理位置授权 | Bool | 否 | 用户授权 | 默认 false |

### 5.2 数据输出
| 数据项 | 类型 | 格式 | 说明 |
|--------|------|------|------|
| 标准化会话 | Conversation | 对象 | 消息列表 + 元信息 |
| 结构化文件 | File | JSON | 供 Persona 引擎消费 |
| 导入统计 | ImportStats | 对象 | 条数、跨度、参与者、告警 |

### 5.3 数据存储
- 存储位置：应用私有沙盒目录
- 存储格式：结构化 JSON（后续可迁移 Protobuf，见 ADR-003）
- 数据保留：由用户控制，可随时删除

## 6. 界面要求

### 6.1 交互流程
```
选择数据源 → 导入数据（iOS：zip/用其他应用打开 → 解压进沙盒；macOS：选目录/授权就地引用）
    → 选择媒体分级档位（默认全部，显示预计占用空间）
    →（可选）设置解析选项 → 解析中（流式，进度可见/可取消）
    → 预处理 → 预览结果与统计 → 确认导入 → 完成
                    ↓（失败）
              显示错误与告警，允许重试/跳过
```

### 6.2 界面元素（信息架构层面）
- 数据源选择列表（微信 / iMessage / 微博 / Instagram / 照片）
- 文件选择按钮与已选文件列表
- 解析进度指示器
- 结果预览卡片（条数、时间跨度、参与者、样例消息）
- 告警/错误列表

> 最终视觉稿在 UI 模块（Phase 4）统一产出，本 PRD 不定义像素级样式。

### 12.2 术语表
- **数据源（DataSource）**：一个可导入的平台，如微信、iMessage
- **解析器（Parser）**：把某数据源的原始文件转成统一 `Message` 的组件
- **预处理（Preprocess）**：清洗、去重、排序的统一管线
- **标准化（Standardization）**：把异构数据统一为 `Message`/`Conversation`
