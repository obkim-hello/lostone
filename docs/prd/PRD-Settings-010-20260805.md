> **Module map (Phase 4 UI).** The user-facing app is split into three modules, each with its own PRD/ERD/Spec trio: **006 Chat Interface** (the chat screen + chat history), **009 Persona Library & Distill** (persona persistence, library, distill flow), and **010 Settings** (this doc — model-management UI on 007 + runtime/mode selection + cloud authorization). This PRD owns the Settings surface. It *builds UI on* Module 007's `ModelRepository` (it does **not** re-implement download/storage/activation) and *produces* the `PersonaRuntimeMode` + `cloudAuthorized` inputs that Module 006 (chat) and Module 009 (distill) read.

## 1. Background & Goals

### 1.1 Background

Modules 004 and 007 delivered end-to-end local inference: `ModelRepository` can download / verify / activate a model, and `PersonaRuntime` (local LiteRT / cloud / fallback) can distill and chat. But today these are exercised only through a debug-only harness (`LlmHarnessScreen`, `kDebugMode`) that hard-codes a `DefaultModelRepository`, keys entry to a raw text field, and persists no user preference. There is no production surface where a user can:

- get their first model onto the device (browse the catalog, pick one for their phone, install with visible progress),
- switch or delete models and see storage usage,
- choose a runtime mode (local by default / cloud opt-in / max-privacy),
- authorize cloud inference and enter a provider API key, or enter a Hugging Face token for gated models.

Modules 006 and 009 both surface "no model installed — install one" prompts; those prompts must route somewhere real. Module 010 is that destination and the single home of user-controlled inference configuration.

The runtime mode + cloud authorization are **inputs other modules read, not settings 010 keeps to itself**: chat (`ChatOptions`) and distill (`LlmBuildOptions`) both take a `PersonaRuntimeMode` + `cloudAuthorized`; `CloudRuntime` enforces the authorization gate internally (SPEC-004 §2.4). Persisting and exposing those two values is a first-class 010 responsibility.

### 1.2 Goals

1. Turn `ModelRepository` into a production **model-management UI**: browse the catalog with device recommendations, install with live progress, activate/switch, delete, and see per-model + total storage/status.
2. Let the user pick a **runtime mode** (local / cloud / max-privacy) and **authorize cloud** (opt-in toggle + provider API key), and enter an **HF token** for gated downloads.
3. **Persist** these choices durably (non-secret settings via Hive; secrets via Flutter Secure Storage) and **expose** `PersonaRuntimeMode` + `cloudAuthorized` via a Riverpod provider that 006/009 watch.
4. Surface every failure honestly and distinctly — each `InstallErrorKind` **actually emitted** by 007's installer (auth required / insufficient storage / unsupported device / network / canceled / unknown) gets its own actionable message; no silent failures, no dead spinners. `corrupted` is mapped defensively (see §"Install states" note) but is not an emitted flow today.
5. Reuse Modules 007 and 004 as-is (only build UI + settings persistence on top); never re-implement download/storage/inference, never persist a secret to Hive or logs.

> **Install states — honesty note (post-#14).** The current `flutter_gemma` installer emits only `downloading → ready` / `failed(canceled | network | unknownModel | authRequired | insufficientStorage | unsupportedDevice | unknown)`. It performs **no** sha256 verification (removed in PR #14 because it was never actually executed), so it **never emits `ModelState.verifying` or `InstallErrorKind.corrupted`**. Both remain **contract-permitted** enum exits (a future self-managed installer may use them), so 010 handles them defensively — but must **not** advertise a verifying spinner or a "verification failed" error as an expected step. This mirrors the honesty fix #14 applied in code; the stale sha256/verifying language in Module 007's own PRD/ERD/Spec (and the `model_install.dart` enum docstrings) is the upstream source of this drift and should be reconciled separately.

### 1.3 Scope

**In scope:**
- **Model management screen** — catalog list (name, size, device-tier recommendation, capabilities, gated 🔒, installed/active badge), install with a `Stream<InstallEvent>`-driven progress bar, cancel mid-install, activate/switch active model, delete (with confirm), storage summary (per-model bytes + total used).
- **Runtime/mode selection** — a `RuntimeChoice` selector (local default / cloud opt-in / max-privacy) mapped to `PersonaRuntimeMode`.
- **Cloud authorization** — an opt-in toggle (`cloudAuthorized`) + provider API key entry (secure storage), with the mode/key relationship made explicit (cloud mode without a key is unusable and is shown as such).
- **HF token entry** — a secure field feeding `ModelRepository.install(..., hfToken:)` (reuse `SecureTokenStore`), required for gated models (Gemma 3 1B).
- **Settings model + persistence** — `AppSettings` (`runtime`, `cloudAuthorized`, `activeModelId`, `chatTemperature`) + `SettingsRepository` (Hive-backed) and a Riverpod provider surfacing it.
- **Entry point** — a Settings entry reachable from the app bar / library (009 home); the "install a model" prompts from 006/009 route into this screen.

**Out of scope (owned elsewhere / deferred):**
- Model download / storage / activation / verification mechanics → **Module 007** (010 only drives its API and renders its events).
- Inference, distillation, chat, cloud HTTP transport wiring → **Module 004** (010 supplies mode + authorization + key; `CloudRuntime` enforces the gate).
- Encryption at rest / biometric lock / backup exclusion for settings + model files → **Module 008** (010 stores secrets via Secure Storage and non-secrets via Hive; the model-file protection hooks are 007/008).
- Persona persistence / library / distill flow → **Module 009**; chat + chat history → **Module 006**.
- A production disk-backed `ModelStore` and disk-free-space precheck (`freeBytes`) → flagged in Technical Debt (DD-002); 010 assumes 007 supplies the store via DI.
- `go_router` navigation → Technical Debt; v1 uses imperative `Navigator`.

## 2. User Stories

### Story 1 — Install a model so I can start talking
> As a first-run user with no model, I want to pick a model suited to my phone and install it with visible progress, so I can start a conversation.

**Acceptance:**
- [ ] The catalog shows each model's display name, size, capabilities, device-tier recommendation, and a 🔒 marker for gated models; the recommended model for my device tier is surfaced first.
- [ ] Installing shows a live progress bar (`downloading → ready`) driven by `InstallEvent`; on `ready` the model is installable-to-active in one tap and marked active. (`verifying` is a contract-permitted state the UI tolerates but the current `flutter_gemma` installer never emits — see §"Install states" note.)
- [ ] A gated model without a token shows an "HF token required" state that routes me to the token field, not a dead failure.

**Priority**: High

### Story 2 — Switch models
> As a user with more than one model installed, I want to switch which one is active and delete ones I no longer want, so I control quality vs. storage.

**Acceptance:**
- [ ] Installed models show state (ready/active) and size; tapping a ready model sets it active (`setActive`) and updates `AppSettings.activeModelId`.
- [ ] Deleting shows a confirm dialog; on confirm it calls `delete`, frees storage, and — if it was the active model — clears active and reflects "no active model".
- [ ] A storage summary shows per-model bytes and total used.

**Priority**: High

### Story 3 — Authorize cloud with a key
> As a user who wants higher quality, I want to explicitly opt into cloud inference and enter my provider API key, so cloud is used only when I say so.

**Acceptance:**
- [ ] Cloud is off by default (`cloudAuthorized == false`, `runtime == local`); enabling it is an explicit opt-in.
- [ ] The API key is entered in an obscured field and stored via Flutter Secure Storage — never Hive, never logs.
- [ ] Selecting cloud mode without a stored key shows an explicit "cloud selected but no key — enter one" state; no network call is possible until authorized + key present (`CloudRuntime` gate).

**Priority**: Medium

### Story 4 — Go max-privacy
> As a privacy-sensitive user, I want a max-privacy mode that never calls any LLM, so I know nothing leaves my device and no model inference runs.

**Acceptance:**
- [ ] Selecting max-privacy sets `runtime == maxPrivacy`; the setting is persisted and surfaced to 006/009.
- [ ] In max-privacy, distill falls back to the Module 003 statistical engine (per SPEC-004) and chat surfaces its explicit disabled state — 010 only records the choice; the enforcement lives downstream.

**Priority**: Medium

## 4. Non-Functional Requirements

### 4.1 Performance
- Install progress UI updates within the 007 progress-callback budget (< 500ms per event; PRD-007 §4.1); the list stays responsive during download.
- Settings `load()`/`save()` are async and do not block the UI; the exposed provider resolves quickly on app start (Hive is local).
- Catalog rendering is O(n) over a small built-in catalog (three entries today).

### 4.2 Security & Privacy
- Local by default: `runtime == local`, `cloudAuthorized == false` on first run; cloud is strictly opt-in (ADR-002/004).
- Secrets (cloud API key, HF token) are stored **only** via Flutter Secure Storage, never Hive, never printed to logs (log-redacted; no full key/token in any log line).
- No model network request happens without an explicit user-initiated install (PRD-007 §4.2); 010 initiates install only on tap.
- 010 never persists chat/persona/import content — it only stores inference configuration.

### 4.3 Usability
- Every install failure is actionable and distinct per `InstallErrorKind`; no dead spinner, no generic "something went wrong".
- The mode/authorization relationship is explicit: cloud-without-key and max-privacy each show what they mean and what they disable.
- Destructive delete is confirmed; the currently active model is clearly indicated.

### 4.4 Compatibility
- iOS 16.0+ (ADR-005); large models require a physical device — the simulator/host tier (`simulatorCpu`) recommends only SmolLM 135M and marks 1B/E2B as over-tier.
- Material Design 3, consistent with the existing `LostoneApp` theme; imperative `Navigator` (no router today).

## 5. Data Requirements

### 5.1 Input
- `ModelRepository.catalog(recommendFor:)` / `installed()` / `stateOf(id)` — read state to render the catalog + installed lists.
- `Stream<InstallEvent>` from `install(...)` — progress/state/error frames.
- Device tier (from 007 `DeviceCapabilities`) — for recommendation + over-tier gating.
- User inputs: chosen `modelId`, `RuntimeChoice`, `cloudAuthorized` toggle, cloud API key, HF token, optional `chatTemperature`.

### 5.2 Output
- Side effects on 007: `install` / `cancel` / `delete` / `setActive`.
- Persisted `AppSettings` (Hive) + secrets (Secure Storage).
- A Riverpod-exposed `AppSettings` (surfacing `PersonaRuntimeMode` + `cloudAuthorized` + `activeModelId`) that 006/009 read.

### 5.3 Storage
- **Hive** (`settings` box) — non-secret `AppSettings`: `runtime`, `cloudAuthorized`, `activeModelId`, `chatTemperature`. (Project tech stack: Hive for app settings.)
- **Flutter Secure Storage** — cloud provider API key + HF token (HF token reuses the existing `SecureTokenStore`; the cloud key uses the same mechanism under a distinct key).
- Model files themselves live in the app documents directory (owned by 007's `ModelStore`); 010 does not manage those bytes.

## 6. Interface Requirements

### 6.1 UI surfaces
- **Settings screen** (entry): sections for **Runtime & Privacy** (mode selector + cloud toggle/key), **Models** (opens/embeds model management), and **Advanced** (temperature). Reachable from app bar / 009 library.
- **Model management screen/section**: a catalog list (recommended-first) and an installed list; each row shows name, size, capabilities, tier fit, 🔒 for gated, and state/active badge; install/cancel/activate/delete actions; a storage summary footer.
- **Progress affordance**: an inline determinate progress bar per installing model (from `receivedBytes/totalBytes`), transitioning directly to a ready/active badge on `ready`. The current `flutter_gemma` installer emits no `verifying` frame, so no verifying spinner is shown; the UI still tolerates the state defensively if a future self-managed installer emits it.
- **Secure entry fields**: obscured API key and HF token fields with a "save"/"clear" action.

### 6.2 Interaction flows
1. **First model**: open Settings → Models → pick recommended → (gated? enter HF token) → Install → watch progress → ready → tap to activate.
2. **Switch/delete**: installed list → tap ready model to activate, or delete → confirm → freed; active cleared if deleted.
3. **Cloud opt-in**: Runtime → select cloud → toggle authorize → enter API key (Secure Storage) → mode + auth persisted and surfaced to 006/009.
4. **Max-privacy**: Runtime → select max-privacy → persisted; 006/009 read it and disable/fallback accordingly.
5. **Routed-in from 006/009**: a "no model installed" prompt pushes the model management screen; on return the caller re-reads readiness.

### 6.3 UI elements
- Catalog row: title + size + capability chips + tier-fit hint + 🔒 (gated) + trailing action (Install / Cancel / Activate / Active ✓ / Delete).
- Runtime selector: segmented/radio control for local / cloud / max-privacy.
- Cloud block: authorize switch + obscured API key field + "no key" warning when cloud is selected without a key.
- Error banner/row: typed to the `InstallErrorKind` with the matching action (enter token / free space / confirm over-tier / retry).

## 8. Acceptance Criteria

### 8.1 Model management
- [ ] Catalog renders with recommendation ordering by device tier; gated models marked; installed/active badges correct.
- [ ] Install streams progress and reaches `ready`; the model can be activated and shows as active; `activeModelId` mirrors the 007 active handle.
- [ ] Cancel mid-install stops the download and returns the row to not-installed (no half-state).
- [ ] Delete (confirmed) frees storage and clears active when the active model is deleted.

### 8.2 Runtime / cloud / privacy
- [ ] Defaults: `runtime == local`, `cloudAuthorized == false`.
- [ ] Cloud opt-in persists `cloudAuthorized == true` and stores the API key in Secure Storage only.
- [ ] Cloud selected without a key shows an explicit unusable state; no network call is possible (gate honored downstream).
- [ ] Max-privacy persists and is surfaced to 006/009.

### 8.3 Error handling (no silent failures)
- [ ] Each `InstallErrorKind` emitted by 007 (authRequired / insufficientStorage / unsupportedDevice / network / canceled / unknown) yields a distinct, actionable UI state; `corrupted` is handled defensively (contract-permitted, not emitted today — §"Install states" note).
- [ ] Gated install without a token surfaces authRequired routing to the token field.
- [ ] Over-tier install is blocked unless the user confirms (`allowOverTier: true`).

### 8.4 Persistence & contracts
- [ ] `AppSettings` round-trips through `SettingsRepository` (Hive); secrets never appear in Hive or logs.
- [ ] The exposed provider reflects saved settings on app start and updates on save; 006/009 read `PersonaRuntimeMode` + `cloudAuthorized` from it.
- [ ] Modules 007 and 004 are reused, not modified.

## 9. Test Strategy

### 9.1 Unit / contract (host)
- `SettingsRepository` against an in-memory/temp Hive box: `load` defaults, `save`→`load` round-trip, secret isolation (secrets go to a fake secure store, never the Hive map).
- `ModelManagerNotifier` with a **fake `ModelRepository`** emitting deterministic `InstallEvent` streams: progress accumulation, each `InstallErrorKind`, activate/switch, delete active, cancel mid-install.
- `SettingsNotifier`: mode/auth transitions, cloud-without-key state, `activeModelId` mirroring.

### 9.2 Widget
- Model management + settings screens with a fake repository + in-memory settings: catalog renders, progress bar updates, typed error banners, confirm-delete dialog, secure fields obscured, mode selector persistence.

### 9.3 Integration / on-device (UAT)
- Physical device (ADR-005): install Gemma 3 1B with a real HF token, activate, verify it powers 006 chat; verify max-privacy and cloud opt-in reach 006/009. Non-blocking for host CI (host = fakes + widget tests).

## 10. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Production disk-backed `ModelStore` + `freeBytes` precheck unresolved (DD-002) | insufficientStorage precheck weak on real device | 010 consumes 007's store via DI; flag DD-002; render whatever `InstallErrorKind.insufficientStorage` 007 emits |
| Harness uses `InMemoryModelStore`; production needs disk-backed store | Wrong store wired in prod | 010 assembles a disk-backed `ModelStore` at the provider layer (not `InMemoryModelStore`); flagged in Technical Debt |
| Secret leaking into Hive or logs | Privacy breach | Secrets only via Secure Storage; log redaction; a host test asserts secrets never touch the Hive map |
| LLM/download non-determinism → flaky UI tests | Flaky CI | All host/widget tests use a fake `ModelRepository` with scripted `InstallEvent` streams; quality judged on-device only |
| Upstream `flutter_gemma` API drift (via 007) | UI breaks | 010 depends only on the stable `ModelRepository` contract, not the plugin |

### 12.2 Glossary
- **RuntimeChoice**: 010's user-facing enum (local / cloud / maxPrivacy) mapped to Module 004's `PersonaRuntimeMode`.
- **cloudAuthorized**: explicit opt-in flag; with a stored key it lets `CloudRuntime` make calls.
- **ModelHandle / active model**: 007's readiness contract; the active model powers 006/009.
- **Gated model**: a model whose download requires a Hugging Face token (`requiresToken`, e.g. Gemma 3 1B).
